# Agent content and map rules

- The public website never exposes backend technology or implementation — not in visible copy, button labels, dialogs, error messages, tooltips, aria labels, alt text, or metadata. No product names, no project host, no SQL, no key names, no file paths, no dashboard instructions. Where records live may only be stated in plain language (資料會同步到你的帳號／資料只存在這個瀏覽器). Setup steps and diagnostics live in this repo (SETUP-SUPABASE.md, scripts/, the browser console), never on the page.
- Every page under `personal/travel/` — the landing page, the two 幕末 itinerary pages, 沖繩 and the world stamp atlas (plus `map/specimen.html`) — runs on one 長崎 travel brand defined in `brand.css`, which is loaded last, after the page's own layout CSS. `brand.css` owns the `--ng-*` tokens, base type and focus ring, breadcrumbs, the sticky top bar, the cover/hero, the diamond lattice, section heads, chips and controls, footers, and one commented pass per page family so `itinerary.css`, `okinawa/okinawa.css`, `map/style.css` and `history-context.css` resolve to brand values. Page CSS must consume the `--ng-*` tokens, use gothic type (display headings at weight 900, never 明朝), keep corners at 8–16 px, and keep decorative shadows to the landing postcard and the soft card-hover lift. New pages link `crumbs.css`, their own layout CSS, then `brand.css` last (the landing page is the one exception: `landing.css` follows `brand.css` because its section layout must win), and carry the diamond lattice (`#an-lattice`) under the page title and above the footer. The landing page's `landing.css` holds only landing-only layout; it declares no tokens of its own.
- Keep page copy concise. A page gets one clear title; every other visible phrase must directly guide a user action, identify content, communicate status, or provide a necessary accessibility/safety/data limitation. Remove decorative slogans, redundant explanatory paragraphs, and filler metadata.
- For travel visit records, capture and display month and year only (`YYYY-MM`). Do not ask for or show a day. Preserve older saved `YYYY-MM-DD` records by migrating them to their month on read; prevent duplicate stamps within the same place and month.
- Show each destination's country flag (bundled `flags/` SVGs) beside country, city, U.S. state, and U.S./Canadian/Japanese park names in the index, the selected-place heading, and the hover tooltip. Entries with no ISO 3166-1 code show no flag rather than an invented one.
- In the major-city layer, show a familiar three-letter city/airport code (for example PDX or NYC) beside the Chinese city name wherever a reliable code exists. Make codes comfortably readable, not tiny metadata. Keep English names searchable and accessible.
- Map colour is the atlas's own system, not a per-stamp decoration: one hue per continent (Asia red, Europe blue, Africa gold, the Americas — north and south together — green, Oceania violet, the unassigned polar entry grey), four tones inside each hue, solved in `map/palette.js` from the real shared borders and the real marker positions so no two touching shapes or neighbouring markers share a colour. Keep the solve deterministic and keep it in the page (no stored colours), keep stamping hue-and-tone-preserving (pale tint when untouched, the same step printed solid when stamped), and keep the index swatches, the place-heading swatch and the legend's continent key in step with it. Colours must stay legible under the crimson ink and navy pins and must not reintroduce decorative multi-hue art.
- Maps must identify major administrative divisions and geographic regions where relevant. Keep political/administrative boundaries distinct from travel-region groupings; do not imply approximate travel regions are official borders. Keep the map free of persistent place/region text overlays; show country, state, park, city, and regional names on hover, and retain clear regional controls. Document when boundaries or locations are approximate.
- Keep the travel atlas destination index populated and selectable alongside the map. Test initial rendering (including JavaScript errors), index availability, and actual map clicks so a missing required DOM element cannot silently disable both interactions and the index.
- A typed term in the destination index searches every collection, not just the open tab: a match on another layer is shown, and choosing it opens that layer and selects the place with the term kept. A term that matches nothing offers to add it as the traveller's own city, with the name carried into the form. The search field stays inside the 地點索引 block; do not relocate it without an explicit design request.
- Keep all 50 U.S. states, the existing 64 U.S. national parks, and 48 Canadian national parks in one North America layer. Retain the original `us:` and `ca:` storage keys so existing stamp records remain valid; allow filters for the U.S., Canada, and their mapped subregions.
- The Stamp Atlas is read-only until someone signs in: a signed-out visitor may browse every stamp but must not be able to add, change, or delete anything, in any mode. The sign-in control (and the current traveller) lives in the sticky top bar, not inside a panel.
- Two sign-in modes share the same files: personal accounts with an invite checked by Supabase on creation when `config.js` has a project URL and anon key (real RLS enforcement, sync, companions, login log), and a browser-only passphrase (`config.localGate`, SHA-256 hash, `scripts/set-atlas-passphrase.cjs`) when it does not. Local mode keeps working with no network client, but it is a soft gate and must be described as one: records stay in `localStorage` and are never presented as shared or secure.
- The access code is never written into this repository or into `config.js`. It lives only as a bcrypt hash in `atlas_access` and is rotated with `select public.atlas_rotate_code('…');` in the SQL Editor. Do not add a plain-code fallback, do not ship a service-role key, and keep the code check in Postgres (`atlas_redeem_code`), never in the page.
- Cloud travellers log in with their own email and password (more than 6 characters). Login and account creation use accessible tabs (arrow keys and Home/End); account creation also requires the shared invite code and confirmed ownership of the email address. A new signup stays read-only while waiting for the confirmation link; resend and return-to-creation remain available, and neither the password nor invite is persisted. Enforce confirmation in `atlas_redeem_code`, `atlas_login`, and `atlas_is_traveller`, not only in the UI. Handle native form submission as well as button clicks, so mobile/password-manager submission cannot just dismiss the dialog. Selecting the active tab must not erase the draft; returning-user login never collects or checks the invite. `atlas_login` only logs existing approved profiles; it must never create one. New accounts use Supabase Auth, never generated credentials stored by the page. Passwords are not written to localStorage; only Supabase's normal session persists. Auth alone grants nothing: only a confirmed email plus a redeemed code creates the `profiles` row required by RLS. Do not restore the retired per-device random-account sign-in. Local/demo modes remain explicitly non-secure.
- Keep `personal/travel/map/SETUP-SUPABASE.md` and `scripts/connect-supabase.cjs` in sync with the functions they describe; the guide must stay short enough to follow click by click. That guide is for the owner and never appears on the page: every failure the page can hit (wrong password, wrong code, too many guesses, account not approved, missing tables or functions, e-mail blocked, offline) is answered with plain language and no setup steps; raw errors go to the browser console only.
- The page must always say where its records live in plain language: the account dialog's sync note and the footer's `資料來源:` line say only that records sync to the traveller's account or stay in this browser — never the service's name, host, or plumbing. If no project is configured, say plainly that the records stay in this browser.
- Public visitors may read every stamp but must never be able to change them. Enforce this in Postgres RLS (`auth.uid() = user_id` plus an approved profile row), not only by hiding buttons; the page may only hold the anon key. A signed-in session that never redeemed the code must remain read-only.
- Stamps belong to one traveller per place per month. Companions are an array of traveller ids on that record; the record's owner is the only traveller who may change the visit, and `atlas_guard_stamp()` keeps the owner fixed, refuses future months, and accepts only approved travellers who allow being tagged. Two people stamping the same place in the same month without a tag are not together.
- "一起走過" lists the records that name both travellers — I tagged them, they tagged me, or a third traveller tagged us both — and reports places and visits separately (`N 個共同去過的地點 · M 次到訪`): one place counts once, each month is one visit. A tagged traveller may remove their own tag with `atlas_leave_stamp()`; that call only ever removes `auth.uid()` from `companions`.
- One data scope per page view, everywhere. A signed-in traveller's map colouring, collection counters, 「只看已蓋章」 filter, hover dates and visit history read that traveller's own records and nothing else; a visitor sees the published atlas from every traveller. `visitsOf()`, `scopeRows()`, `isStamped()`, `stampCount()` and `stampDetails()` are the only entry points for that scope — do not reintroduce a second one that reads all rows while signed in. Another traveller's companions are never merged into mine. Switching accounts clears the previous traveller's queued rows, restored cache and selections.
- Every stamp write is optimistic and queued in `eva.travel.atlas.outbox.v1` so a dropped connection cannot lose it. Keep the outbox, the per-user cache, and the realtime subscription consistent when changing sync code.
- Never claim the cloud has a record it has not confirmed. Each record shows its own state (`待同步` while queued, `已同步` only after the server accepted it, `未同步` with a 「重試」 button after a refusal), the stamp feedback and status line say the same, the stamp button is locked while a request is in flight, and the upsert stays keyed by traveller + place + month so a retry or a double tap cannot create a second stamp. The per-user cache is identity-checked before it is shown.
- Removing a stamp is destructive and synced: the × always asks for confirmation naming the place and month, and cancelling changes nothing.
- Password recovery is part of account access: 「忘記密碼？」 on the returning-user login requests the reset mail with this page as the redirect, and a recovery link opens the same dialog on its 重設密碼 view, which collects only a new password. Keep the redirect URL documented in SETUP-SUPABASE.md so the mail can come back.
- `?demo=1` (or `config.demoMode`) must stay a local-only demonstration: seeded travellers, `localStorage`, and `BroadcastChannel`, never a real project.
- A homepage section carries a title only — no descriptive copy beside the section heading. On the site homepage (`index.html`), every work entry shows its title with no role/affiliation line or topic-tag line beside it. On the travel landing page (`personal/travel/index.html`), each section head keeps only its numbered eyebrow and title; descriptions beside headings are removed, and any copy that guides a user stays in the section body.
- Stamps, month records (到訪月份) and sign-in live on the world stamp atlas (`personal/travel/map/`) only. The travel landing page never mentions stamps, month records, sign-in, or record storage/sync — it only sends one postcard. Remove any such copy from the landing page: side descriptions beside section heads, the postcard letter, storage/sync notes, and month labels on photographs. The postcard itself keeps its stamp, postmark and hanko decoration and its single call to action linking to the atlas.
